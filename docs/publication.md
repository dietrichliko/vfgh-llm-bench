# Publication: Zenodo, OSF and the study repository

As of 2026-10-29. This document explains how the study protocol and results are recorded and published. It is built from two services, Zenodo and OSF, plus a git repository that the app writes to. For the design of the study itself, see [paper.md](paper.md).

## 1 Zenodo

[Zenodo](https://zenodo.org) is an open research repository run by CERN. Anyone can deposit research outputs there for free: code, data, slides, papers.

- **DOIs.** Each published record gets a DOI (registered with DataCite), so it can be cited like a paper.
- **Versions.** A record can have several versions:
  - The **concept DOI** always points to the latest version. Use it to cite "the study" in general.
  - Each version has its own **version DOI**. Use it to cite exactly what a result was based on.
- **Immutable files.** After publishing, a version's files cannot be changed or deleted, only its metadata. A correction becomes a new version. This is what makes Zenodo usable as a timestamped proof.
- **GitHub integration.** Enable a GitHub repository once in Zenodo's settings. From then on, every *published GitHub release* of that repository is archived automatically as a new Zenodo version with its own DOI. A `.zenodo.json` or `CITATION.cff` file in the repository controls the metadata: title, authors, licence, related identifiers.
- **Access.** Records can be open, embargoed (public from a set date) or restricted (files on request). The metadata is always public.
- **Size.** Up to 50 GB per record by default, which is far more than this study needs.
- **Licences** we would use:
  - **Code:** MIT, as in the old project.
  - **Data and results:** CC BY 4.0.
  - **VfGH decisions:** official works under § 7 UrhG, with no copyright, so they can be included as they are.
  - **Model outputs:** check the terms of each provider before publishing; open-weight models via OpenRouter are normally unproblematic.

## 2 OSF and pre-registration

[OSF](https://osf.io) (Open Science Framework) is a free platform run by the non-profit Center for Open Science. Among other things, it is used for **pre-registration**: a public, timestamped record of what a study will test and how, made **before** any results are seen.

- **What is registered:**
  - research questions and hypotheses;
  - data and selection rules;
  - design;
  - planned analysis, with metrics, tests, thresholds and exclusions.
- **Templates.** OSF offers several, including "OSF Preregistration" (the standard, detailed one) and an "AsPredicted"-style short form. For this study the standard template fits: the model outputs are new data, generated by the study.
- **Freezing.** A submitted registration is read-only, timestamped and gets a DOI. It can be made public immediately or **embargoed for up to 4 years**.
- **Updates.** Changes after registration are filed as updates with a reason. The original stays visible, so readers see what changed and when.
- **Confirmatory vs. exploratory.** A pre-registration separates results that were planned and tested as planned (confirmatory) from those found along the way (exploratory). Both are legitimate, but the reader can tell which is which.

**Why it matters here.** LLM studies have many choices that could be adjusted after seeing results:
- prompt wording;
- which cases are included;
- which judge criteria are reported;
- the agreement threshold;
- how invalid outputs are treated.

Registering these beforehand protects the study against the reproach that the setup was tuned to produce a message. That matters for a politically charged topic like the AVG amendment.

## 3 How they fit together

| | Study repository: git tag + Zenodo | OSF registration |
| --- | --- | --- |
| Content | Technical details: cases, prompts, model config, versions, results | The scientific plan in prose: questions, hypotheses, analysis, exclusions |
| Audience | Someone who wants to check or reproduce the study | Reviewers, readers, the conference audience |
| Written by | The app (Freeze protocol / Publish results) | The authors, by hand on osf.io |
| Timestamp and DOI | Yes, via the Zenodo version DOI | Yes |
| Recognised as pre-registration | Not formally | Yes |

The OSF registration links to the protocol tag and its Zenodo DOI. The study repository's README links back to the OSF registration. The dashboard and every export show the protocol tag and hash they are based on.

## 4 Plan for this project

### Study repository

A separate public GitHub repository (working name `vfgh-llm-bench-study`), apart from the code repository. One code version can serve several studies, and the record stays clean.

```
studies/<slug>/                 e.g. studies/conference-2026/
  protocol.yaml                 study name, date, conditions, repetitions, phrasings, cutoff rule
  cases.csv                     RIS document number, case number, date, sha256 of the XML, parser version, flags
  models.yaml                   model id, provider, pinned provider and quantization, cutoff, role, tool mode
                                (secret names only, never values)
  prompts/*.md                  full text of every prompt version
  analysis-plan.md              metrics, thresholds (e.g. κ ≥ 0.7), baselines, exclusions
  environment.yaml              app commit and image digest, bridge, ris-mcp and pydantic-ai versions
  AMENDMENTS.md                 every change after freezing, with date and reason
  results/                      added at the end: runs, scores, ratings (JSON Lines/CSV, gzipped),
                                static dashboard
```

### What the app does

1. **Freeze protocol** (admin button):
   - The app writes the files above, stores the snapshot and its sha256 in the database, and locks the order's configuration.
   - It commits to the study repository, sets an annotated tag `<slug>-protocol-v1` and pushes.
   - It authenticates with an SSH **deploy key** that can write only to that repository, passed into the container as a secret (`STUDY_REPO_URL`, `STUDY_REPO_DEPLOY_KEY`).
   - **Fallback:** without a key, the app offers the same snapshot as a ZIP download to commit by hand.
2. **Amendments:** a change to a frozen order requires a reason. It produces `protocol-v2` and an entry in `AMENDMENTS.md`. Every run records the protocol version it ran under, and runs outside the frozen protocol are flagged as deviations.
3. **Publish results:**
   - The app commits `results/` and tags `<slug>-results-v1`.
   - Raw model responses go into the repository only if they are small enough. Otherwise they become a file attached to the GitHub release (also archived by Zenodo), and the repository keeps their sha256 hashes.

A GitHub release created from each tag triggers the Zenodo archive and DOI.

### Timeline for the conference

1. Test the pipeline on the pilot case V 251/2025. This is a test, not a result; the OSF registration says so.
2. Finalise the prompts (approved by the legal expert), the case list (~20 judgments) and the model list (open models with known training cutoffs).
3. Click **Freeze protocol** → tag `conference-2026-protocol-v1` → publish a GitHub release → Zenodo DOI.
4. **OSF registration** with the standard template, linking to the protocol DOI. Declared as an **exploratory pilot**, with 2–3 confirmatory hypotheses, for example:
   1. The tested models beat the "always unlawful" majority baseline.
   2. Condition C changes outcome accuracy compared with condition A.
   3. The tested models judge the sham reasoning as legally sound in more than X % of cases.

   Everything else is reported descriptively.
5. Run the study in the app.
6. Click **Publish results** → tag `conference-2026-results-v1` → GitHub release → Zenodo DOI.
7. Methods slide: "Pre-registered: OSF DOI … · Protocol, data and code: Zenodo DOI …".
